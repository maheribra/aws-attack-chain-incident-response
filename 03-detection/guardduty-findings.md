# GuardDuty Findings

## Purpose

This document records the GuardDuty verification performed for the AWS Attack Chain and Incident Response laboratory.

## Verification Scope

The simulated attack was executed in AWS account `<ACCOUNT_ID>`.

The attack chain included:

1. Authentication as the lab attacker IAM user.
2. Attempted privilege escalation through IAM role assumption.
3. Use of temporary STS credentials where successful role assumption occurred.
4. Access attempts against vulnerable AWS resources.
5. Retrieval of simulated sensitive data.

The attack activity was investigated using AWS CloudTrail evidence.

## GuardDuty Verification

GuardDuty was checked directly in the attack-chain lab account using the AWS CLI.

The verification returned:

DetectorIds: []

This confirms that no GuardDuty detector was enabled in AWS account `<ACCOUNT_ID>` at the time of verification.

## Detection Result

GuardDuty did not detect the simulated attack.

The reason is that GuardDuty was not enabled in the attack-chain lab account. Therefore, no GuardDuty findings were generated during the attack simulation.

This is documented as a detection gap rather than a GuardDuty failure.

## Confirmed Detection and Forensic Evidence

The primary evidence of activity was obtained from AWS CloudTrail.

CloudTrail records confirmed:

- Activity performed by the lab attacker identity `aws-attack-chain-lab-attacker`.
- Multiple STS GetCallerIdentity API calls during the attack timeframe.
- STS-related activity recorded within the AWS account.
- Additional AssumeRole events generated by AWS service roles, including Resource Explorer service-role activity.

CloudTrail provided the audit history required to investigate API activity and reconstruct events during the simulation.

## Detection Gap

The attack chain demonstrated that CloudTrail can provide valuable forensic evidence after suspicious activity occurs.

However, because GuardDuty was not enabled, the environment did not generate automated threat detection findings for the simulated attack.

This highlights the importance of enabling GuardDuty and combining AWS native detection services with CloudTrail investigation capabilities.

## Conclusion

GuardDuty verification was completed in the attack-chain lab account.

The result was:

- GuardDuty detection of the attack: No
- GuardDuty detector enabled: No
- GuardDuty finding generated: No
- CloudTrail evidence available: Yes
- CloudTrail useful for investigation: Yes

The project demonstrates how CloudTrail can support incident investigation while identifying the absence of GuardDuty monitoring as a security detection gap.
